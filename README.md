# Spec-Driven Development Harness Engineering

This repository demonstrates a GitHub Spec Kit-based workflow for building software under a harness that enforces specification compliance, independent validation, and human acceptance.

The project includes two small applications:

- Part 1A: deterministic application with exact, repeatable behavior.
- Part 1B: AI-influenced application whose outputs vary but remain bounded by a validation harness.

The workspace follows a spec-driven pattern where the approved specification is the source of truth and the code is generated against it.

## Repository structure

- `.specify/` — foundation definitions, templates, and governing principles.
- `specs/` — authoritative requirements, plans, and task breakdowns for each app.
- `apps/deterministic_invoice/` — deterministic behavior demo.
- `apps/ai_briefing/` — non-deterministic AI-like behavior demo.
- `harness/` — validation harness and evidence capture.

## Part 1A — deterministic software behavior

The deterministic app is an invoice calculator with strict rules:

- subtotal must be non-negative
- tax rate must be between 0 and 1
- valid discount codes: `SAVE10`, `VIP15`
- shipping is $0 when subtotal >= $100, otherwise $10
- final total is rounded to two decimal places

This app is predictable because each input produces exactly one output.

## Part 1B — non-deterministic AI behavior under constraints

The AI-style app simulates an assistant that generates a project briefing from freeform meeting notes.

It uses randomness to model AI variability but the harness validates:

- required keys exist
- summary length stays within bounds
- risk is from an allowed set
- no more than 5 action items
- action item wording is concise and compliant

If an output violates the spec, the harness writes structured failure evidence and treats it as actionable feedback for correction.

## Spec Kit workflow in this repo

1. Requirements are authored as approved specs under `specs/`.
2. Implementation is generated from the spec, not the other way around.
3. A separate validator checks behavior independently from app logic.
4. Failures are captured as JSON evidence.
5. Human approval is required before accepting a build.

## Run the demonstrations

From the repository root:

```bash
python3 harness/spec_harness.py
```

This script runs both apps and writes validation evidence to `artifacts/evidence/` when instructed.

## Human acceptance decision

This project is designed to require a final human sign-off before considering the work complete. The harness records the evidence and leaves the final decision to a human reviewer.
